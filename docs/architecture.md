# 架构

## 角色划分（PRD §1 / §4）

| 角色 | 承担 | 不做什么 |
|---|---|---|
| **ESP32 终端** | 按住录音、上传、状态显示、结果播放、取消 | 不理解语义、不直接控制手机 |
| **主机连接程序 `host/`** | 收音频→STT、送文本给 Agent、回传状态/追问/结果、TTS、任务串行闸门 | 不自己做 Agent 推理、不写死微信/邮件业务 |
| **Hermes Agent** | 对话、模型调用、工具使用、会话记录、定时调度（`hermes cron`） | — |
| **iCTRL** | 提供手机操作能力：观察界面、打开 App、点击、输入、滑动、核查（JSON-RPC 2.0 :8200） | — |
| **iPhone** | 微信 / 邮件等真实 App 的载体 | — |

> 关键约束：**微信、邮件不是独立业务模块**，统一走 iCTRL 操作手机 App。
> 不引入 Gmail API / IMAP / 邮箱授权页 / 自研 Agent Runtime / 独立调度器。

## 连接拓扑

```
                        ┌──────────── Mac mini / 本机 ────────────┐
                        │                                         │
   ESP32-S3 ──WiFi──►  host/bridge (WebSocket, 认证)              │
   (音频/状态)          │   ├─ STT/TTS                            │
                        │   ├─ 任务闸门 (同一时刻仅一个手机任务) │
                        │   └─ Agent 适配层 ──► hermes -z / serve │
                        │                        │                 │
                        │                        ▼                 │
                        │                   iCTRL JSON-RPC        │
                        └────────────────────────┼────────────────┘
                                                 ▼
                                            iPhone :8200
```

- ESP32 通过 **WiFi** 连主机；USB 线只用于供电/烧录/调试（PRD §7）。
- 主机通过 **iCTRL** 连 iPhone（需手机开启 Remote Access，且与主机同网段）。
- 终端连接需认证；协议只覆盖：语音、任务状态、补充/确认、取消、结果（PRD §7）。

## 手机任务串行闸门（PRD §5.2）

微信、邮件、定时任务共用一台手机，`host/bridge/tasks.py` 用**单一串行队列**保证：

- 同一时刻只有一个手机任务在跑；
- 用户主动任务优先，定时检查在空闲时才提交；
- 重复到期的同类检查合并为一次；
- 用户手动操作手机导致页面变化时，Agent 重新观察，不能确认就停止并说明。

## 结果真实性（PRD §5.3）

- 取消 = 停止派发**后续**动作，已发生操作不自动撤销；
- 可能已发送时**不能只显示"已取消"**，要如实说明；
- 设备重连不重复提交旧录音；重复 `request_id` 返回已有状态，不重跑；
- 无法确认外部操作是否完成 → 状态 `unknown`（"结果未确认"），交由用户核对；
- 吃不下证据的成功提示就是造假：没看到发送证据不报"已发送"。

## 状态模型（PRD §5.1）

ESP32 屏幕只需 5 态 + 结果分类：

```
idle → recording → processing → { need_user | result | offline }
result := success | failed | cancelled | unknown
```

桌宠动画只是这些状态的表现，不假装知道执行进度。
