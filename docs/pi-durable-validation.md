# Pi Durable 验证与是否接入的判断

日期：2026-10-17。以下保留**迁移前的隔离验证记录**，当时未替换生产 Agent。此后用户已授权迁移，正式实现位于 `host/pi/`，默认后端现为 `pi`；部署和恢复以 [运行时文档](../host/pi/README.md)及[项目总结](PROJECT-SUMMARY.md)为准。下面的延时边界仍然适用，生产迁移不等于已证明全面提速。

## 结论

Pi Durable 已证明能够承担会话持久化、模型与工具循环、上下文压缩和中断恢复。
它可以减少未来自建通用运行时的工作，但此次验证**没有证明现有生产代码会显著变少**。
当前 Bridge 已经有较短的直接调用循环，手机、语音、安全取消和业务记忆规则仍需维护；
Pi 还引入一个 Node 子进程和 Python/Node 适配边界。

基础能力验证通过，受控延时测试通过初步门槛。真机样本少，且读屏 P95 曾超出增幅 10% 的目标，
因此尚不满足直接替换默认后端的完整验收条件。当前保持生产架构。

若近期目标主要是记住偏好、笔记和历史订单，在现有 Python 链路增加结构化 SQLite 记忆更直接。
若完整会话持久化、上下文压缩、跨进程恢复确定属于近期需求，Pi 是已验证可用的候选，
接入理由应是减少这部分基础设施的自研，而不是承诺显著减少现有代码或自动提速。

## 对现有实现能简化多少

| 现有部分 | Pi 可接管的内容 | 仍需项目维护的内容 |
| --- | --- | --- |
| `direct.py` 的 Conversation、messages、`_pending` | 持久 Conversation、Entries、Documents | 任务输入整理、手机证据与结束结果校验 |
| `direct.py` 的模型与工具迭代 | generation/tool tasks、正常回合推进 | 千问配置、超时、步数预算、不确定结果闸门 |
| 尚未具备的会话恢复、压缩 | SQLite 恢复、提交去重、compaction | 恢复前核对手机实际状态、压缩策略 |
| `tasks.py` | 部分通用生命周期可迁移 | 手机独占、队列、NEED_USER、取消后的安全收尾 |
| `server.py`、固件语音状态机 | 持久保存对话相关状态 | 播报完成回执、收音、VAD、唤醒、长按键、任务归属 |
| 长期记忆 | Documents 可保存自定义 JSON | 偏好/笔记/订单含义、证据、日期、检索、修改、删除 |
| `phone_tools.py`、`processes.py` | durable tool intent 与恢复分类 | 手机 RPC、进程清理、有效 ref、启动失败和不重复操作 |

不能整体删除 `tasks.py`、`server.py` 或 `processes.py`。
实验目录大部分是适配、测试与测量代码，不能以它的总行数预测正式接入后的净删减量。
本轮未实施生产替换，因此“实际净减少多少行”仍未验证。

## 实际验证范围

采用官方 `@earendil-works/pi-durable` 1.3.0、Node 24.20.0，依赖精确锁定。
模型使用项目有效配置 `qwen3.8-flash`，实际发出请求的 `enable_thinking=false`、
`parallel_tool_calls=false`，输出上限 384 tokens、请求超时 30 秒。
未启用 shell/coding tools、Code Mode、图片处理或子 Agent。

常规实验运行一个 Node Pi 进程和一个 Python 工具适配进程，数据库仅由 Node 所有。
语音集成测试另启动临时本机 Bridge 作为测试设施，物理 ESP32 保持连接生产服务。

| 验证项 | 结果 | 边界 |
| --- | --- | --- |
| 一次记住多条偏好 | 单次模型请求写入美式、热、不加糖三条记录 | 在提交完成后才认为记住成功 |
| 重启后召回 | 关闭并重新打开运行时、清空 transcript 后仍准确召回 | 验证来源为独立 Memory Document |
| 临时与长期要求 | “今天换拿铁”不覆盖长期美式；“以后改拿铁”更新原偏好 | 当天覆盖按上海日期失效；任务覆盖绑定任务 |
| “昨天的咖啡” | 准确选择昨日已核实记录，排除未完成及未核实候选 | 使用测试订单；没有创建真实订单 |
| 语音澄清 | 真实 ASR → Pi → 真实 TTS → speak_done → listen → 真实 ASR 回答 → Pi → 真机读屏 | 播放回执由虚拟终端发送，未把物理小精灵切到 Pi |
| 提问期间暂停 | 回答前 0 次手机 RPC，识别到“热的”后 1 次 page_source，任务号不变 | 此流程只读，无点击或交易 |
| 前置整理取消 | 观察到 preparing 后取消，约 2.2 毫秒完成；立即取消也不派发手机动作 | 前置 HTTP 请求可取消，持久状态为 cancelled |
| 取消与恢复 | 14 项专项测试全部通过，包括运行中取消、RPC 收尾、队列撤回和 SIGKILL 重开 | 可控故障测试；并非物理按键/声学取消全矩阵 |
| 请求去重 | SQLite 重开后相同 request ID 返回原 submission | 不等于外部手机动作恰好执行一次 |

原有 host 测试另运行 121 项：120 通过、1 项可选 Hermes 测试跳过；独立任务测试 9 项通过。
本轮原有测试合计 129 通过、1 跳过，新增 Pi 专项 14 项通过。

## 延时与资源

固定真实淘宝页面与启动响应做重放，避免页面动态内容改变。两种后端每个场景各 20 次，
交错先后顺序，分别预热。使用相同系统提示、受限工具定义及生产整理器校验后的共同计划。
下表是执行阶段，包含模型、IPC、工具封装和持久化；不包含共有的任务整理、ASR、用户等待和播报。
Direct 使用现有非流式 JSON，Pi 使用官方 provider 的 SSE；这是两种实际接法的比较。

| 受控场景，每侧 n=20 | Direct 中位数 | Pi 中位数 | 中位数变化 | Direct P95 | Pi P95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 读取当前页面 | 2.251 秒 | 2.383 秒 | +5.9% | 3.747 秒 | 2.932 秒 |
| 打开淘宝并读取页面 | 2.518 秒 | 2.568 秒 | +2.0% | 4.458 秒 | 3.208 秒 |

两个受控场景的 P95 均满足“不比 Direct 增加 10%”的初步门槛。
常规执行均为两轮模型请求。打开应用场景 Direct 有一次进一步读取完整快照，达到五轮；Pi 本轮均为两轮。
这不是 Pi 固定节省了三轮，而是模型在大页面上存在不同的读取选择。
P95 数字较低也不能据此宣称 Pi 普遍更快；20 次样本不能证明线上尾延时。

真实手机每侧每场景另测 3 次：

| 真机场景，每侧 n=3 | Direct 中位数 | Pi 中位数 | Direct P95（本样本最大值） | Pi P95（本样本最大值） |
| --- | ---: | ---: | ---: | ---: |
| 读取当前页面 | 2.911 秒 | 2.871 秒 | 2.917 秒 | 3.973 秒 |
| 打开淘宝并读取页面 | 3.259 秒 | 3.437 秒 | 3.811 秒 | 3.553 秒 |

真机读屏尾部数值增幅约 36%，尚不能确认满足 10% 目标。
其中 Pi 最慢读屏样本的模型阶段为 3.225 秒，其他阶段合计 0.748 秒；
Direct 最慢读屏样本分别为 2.268 秒与 0.649 秒。
该分解表明这次差异主要位于模型阶段，不能仅凭这个小样本认定框架存在固定一秒开销。

进一步移除云端波动，固定两轮模拟模型和同一页面，运行本地封装 100 次：

| 本地执行，无云端、无真实手机动作 | 中位数 | P95 |
| --- | ---: | ---: |
| 原 Direct 循环与工具封装 | 3.28 毫秒 | 3.79 毫秒 |
| Pi SQLite、IPC 与工具封装 | 8.77 毫秒 | 11.32 毫秒 |

两者 P95 相差约 **7.54 毫秒**。测试包括实际文件日志与工具封装，Pi 包括持久化；
它衡量本地增量成本，不能替代云端或真机验收。

受控云端测试结束时 Node RSS 为 99.3 MiB，工具适配 Python RSS 为 36.3 MiB；
真机测试结束时 Node 约 98.9 MiB、Python 约 40.3 MiB。
这些是进程 RSS 快照，不是空闲稳态、峰值或生产新增内存的精确预测。
本地安装的 `node_modules` 约 111 MiB，未导入的可选能力仍有安装体积。
它适合在现有主机评估，不能描述成“几 MB、零进程成本”的库。

## 记忆规模和压缩

3324 条测试记忆（3000 条订单、300 条笔记、24 条偏好）存入 SQLite：

- 关闭重开并首次读取约 5.21 毫秒。
- 本地 snapshot、按日期筛选和序列化 100 次，P95 约 0.162 毫秒。
- 交给模型的选取结果为 2103 字符，数据库约 772 KiB。

这里使用简单字段筛选和有界上下文，未引入向量库或 embedding。
笔记的通用语义检索、冲突处理与用户编辑/删除仍未实现，不能把存储能力等同于完整长期记忆产品。

真实模型对 72 条测试历史做手动压缩，用时约 5.13 秒；压缩请求输入约 22686 字符，之后核对请求的输入为 1963 字符。
原始 72 条记录仍在 SQLite 中，最新任务 R100 的等待回答状态和独立保存的咖啡偏好仍能召回。
本次压缩使用 1 次模型请求，之后核对记录再用 1 次。
普通任务测试关闭自动压缩；正式策略应提前压缩并保留任务检查点，不能每次唤醒都先等待摘要。

## 验证中发现并处理的问题

1. Pi 的 hook 抛异常会被隔离，不应把它作为唯一阻断机制。
   原型改为在模型派发前读取持久保护位，手机调用前提交 pending intent，确认结果后清除；
   interrupted/unknown 阻断后续请求和动作，不能由模型自行重试。
2. 手机工具均声明 unsafe。重开后不盲目重放；safe 工具测试也使用外部幂等键，不能省略外部对账。
3. 原型曾使用长 provider call ID 作为完成凭据，增加模型输出成本；现已沿用现有 `e1` 等短任务凭据。
4. 初轮重放启动响应带有合成标记，最终对比改用真实手机启动响应和真实页面。
   初轮较差的延时报告保留在本地，不用作最终表格；模型偶发继续读完整页面的问题仍如实统计。
5. 真机预检发现 Runner 进程存活但 XCTest UI 授权已经失效。
   根据原始日志恢复 Runner 后再测。生产 Bridge 未重启，配置与固件未更改。
6. 通用 Agent 可以用自然语言结束，手机任务仍须沿用现有结构化结束与证据校验。
   原型补齐与 Direct 一致的 finish_task/ask_user 要求；同时把任务整理阶段的取消传递到 Python HTTP 请求，
   取消清理失败必须报告错误，不能返回“已取消”。

云端 A/B 表格对应报告中的源文件哈希。其后补充的是前置整理取消及结构化结束校验，
未改变正常结构化完成的执行策略；正式接入时仍须使用最终生产适配器重新做性能验收。

## 正式迁移前的具体要求

若继续采用 Pi，应让它替换现有通用执行循环，而非在现有 Agent 前再增加一次必经模型整理。
保留同一千问服务、关闭思考、串行手机工具和现有语音协议，由 Bridge 管理一个常驻 Node 子进程。
生产持久数据应使用独立持久目录，不沿用实验 `.runtime/`。

在改默认后端之前仍需完成：

- 将现有 TaskManager 的开始、等待回答、取消、完成与 Pi 持久状态做一致性接入，避免两套生命周期漂移。
- 在统一手机资源闸门下验证中断核对、取消清理和重连，并把有效步数/时限预算接入。
- 扩大真实手机延时样本，验证 P95 目标和模型读取策略；进行物理终端播报、收音、长按与语音取消实测。
- 实现可查询、修改、删除且可追溯的记忆接口；真实订单以实际凭据为准。

这些属于正式实现，不在本轮隔离验证中自动启用。

## Jev 决策层的后续评估（未接入）

2026-10-17 核对了 TypeSafe AI 的 Jev。它返回 Choice、Score、Noul 等受限答案，
适合从已知选项做判断，不能直接代替自由文本计划和回复的生成。
官方公布的 70–500 毫秒是其测试环境结果，并注明评测多来自美国西海岸，不代表本机测量。
官方模型说明也指出英文效果最好，CJK 需要用实际内容验证。

在现有架构中，可以让代码从当前页面和任务状态构造少量合法动作候选，
由 Jev 选择候选 ID，现有 PhoneTools 继续校验与执行；无法可靠选择时才回退千问。
Jev 不产生新的任意手机动作。另一个候选点是意图路由，但必须能让常见路径跳过原有模型调用，
否则只会在既有千问请求之前多加一次网络等待。

| 判断内容 | 建议 |
| --- | --- |
| 选择合法页面动作、识别页面类型 | 值得用脱敏读屏记录离线回放比较 |
| 在已检索的订单/商品候选中做语义选择 | 可以评估；价格、日期、距离计算仍由代码完成 |
| 取消、任务归属、超时、步数预算 | 保留现有确定性代码 |
| 生成任务步骤、搜索词、提问和结果文字 | 保留千问 |
| ASR、TTS、应用启动和 iCTRL RPC | Jev 不直接缩短这些阶段 |

单次决策的串行级联近似为 `T_Jev + 回退率 × T_千问`。
只有这个值小于被替换的千问判断时间，且实际错误率没有恶化，才构成净收益。
应测中文准确率、回退率、P50/P95 和整任务耗时，而不只测 Jev 单接口速度。

Jev 可以通过 Python/HTTP 独立接入，不依赖迁移 Pi。已安装的 pi-ai 也含 TypeSafe classifier provider，
但本项目尚未配置或调用 Jev，当前生产模型服务仍全部使用千问。

[模型与语言支持](https://docs.typesafe.ai/models)、[能力限制](https://docs.typesafe.ai/model-jaggedness/jev-1.13)、
[受限参数的工具调用示例](https://docs.typesafe.ai/cookbooks/function_calling)。
