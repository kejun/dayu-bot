# 正式 Pi Durable 运行时

生产入口为 `main.mjs`，版本锁定 `@earendil-works/pi-durable`、`pi-ai`、`chord` 1.3.0。需要 Node >=22.19.0。在 `host/` 执行 `npm --prefix pi ci --ignore-scripts`，再按根目录 README 安装 Python editable 包并启动 Bridge。`experiments/pi-durable` 是早期验证程序，不是部署入口。Pi SDK 当前是实验版本，升级必须重新跑取消、重启与真实手机验收。

## 边界

- Python：认证、ASR/TTS、播放回执、串行 FIFO、任务规范校验、手机 RPC 的有界执行与安全收尾。
- Node / Pi：千问模型循环、顺序工具、对话上下文、按需压缩、任务状态及用户记忆。没有 shell、代码执行、多 agent 或 Jev。
- 两进程通过 stdin/stdout JSONL 通信，凭据只通过管道传递，不放在启动参数和数据库中。模型及压缩调用都使用现有千问配置，固定关闭思考与并行工具。

每个任务单独一个 Pi conversation；追问后仍用同一 conversation。长期记忆在 session 层按设备 owner 隔离，仅取有限条偏好、笔记和相关订单；不把整个历史装进每次提示。明确记忆对话跳过手机规划和手机工具，保存成功之后才播报。临时偏好按 Asia/Shanghai 日期生效；新指令优先。

`remember_order` 必须有当前真实订单详情页的证据，代码核对完成状态、唯一订单编号、商品、店铺与日期才保存。候选、待付款、退款、失效页面不能变成“昨天下单”的事实。当前项目仍禁止最终提交订单/支付，因此不会凭“已选商品”自动生成成交记录。历史订单的跨 App 实机验收仍需真实完成订单样本。

## 持久化与恢复

`BRIDGE_PI_DATA_DIR` 默认 `~/.dayu/pi`，目录权限 0700，SQLite 0600。包含用户原话、页面、偏好等本地私有数据，备份时先正常停 Bridge，复制整个目录。不要只复制仍在写入的 SQLite 主文件。API Key 保留在 `.env`；数据库及日志不能提交远程仓库。

任务入队、追问、回答、结果先提交 Pi，再向终端发布。相同 request_id 重启后仍去重；启动时加载所有未完成任务及最近 200 条终态用于协议重放。等待回答的任务会在设备重连后重播问题并听取回答。排队任务继续按原顺序执行。

手机动作在派发前先把唯一 `operation_id`、参数和进度提交到 Pi；Runner 在派发前保存按认证客户端隔离的回执。相同编号不会重复执行。单次 RPC 超时后，Bridge 最多等待 `PHONE_RECOVERY_TIMEOUT`（默认 45 秒）查询原编号，确认成功后读取新画面并继续同一任务。不会重发点击、输入或翻页。

仍无法确认时，原任务保留为等待状态，Pi 可继续诊断、核实回执和重新规划；准备结束前会再核实一次。收到“继续”后先核实原动作，成功后接续剩余目标。带编号的执行中动作在 Bridge/Node 中断后也先查询原回执，再恢复，不能重放。Runner 自身重启前仍未完成的回执标为 `unknown_after_restart`，不能凭推测算成功。

只有主机进程无法确认清理，或旧版无回执的动作仍无法核实时，才保留人工核对保护；不把新请求直接结束为失败。明确记忆对话不因手机动作等待而被运行时拒绝。遗留保护的人工恢复流程：

1. 正常停止 Bridge，核对手机界面与是否发生点击、发送或下单。
2. 在 `host/` 执行 `./.venv/bin/python -m bridge.cli pi-recover`。命令拒绝并行 Bridge、未结束的 RPC 进程或无法读取的手机；成功读到当前界面后才解锁通道。
3. 重新启动 Bridge，必要时由用户重新发起旧任务。旧任务的 unknown 结果不会被改成成功，也不会重放。

Python flock 和 Node runtime.lock 防止两个运行时占用同一目录；不同目录不提供同一手机的跨目录锁，禁止用多个目录/回退后端绕过串行控制。运行时丢失连接后不自动重启或切换模型后端，以免重复副作用。保留 direct / Hermes 代码用于显式回退；旧内存队列不会伪装成已经迁入 SQLite 的历史任务。

## 取消、性能与验证

控制取消直接走 Bridge → Pi abort → 手机 RPC 收尾，不等待模型决策。等待已发出的 XCTest 动作有界返回后才播报取消；清理失败保持 unknown 和暂停。取消不能撤销已经发生的操作。

明确的只读元素未找到会回交模型，按最新界面重新定位；Runner 明确返回控件树无响应且查找已结束时，回交模型改用 OCR。AX 无响应的分类仅适用于严格匹配的 `find_element` 已结束错误。连续三次错误、连续四次页面无变化，或模型准备放弃时，会把原始目标、已完成动作、错误和当前界面交给 Pi 的 `replan_task` 重新规划，继续剩余步骤；最多三轮新策略仍无进展才询问用户。新计划不能扩大原任务的应用和只读权限，也不能丢掉原有约束。未确认的动作先查询回执，重新规划不允许重发不确定的点击、输入或提交。终态播报使用中文原因，不朗读底层 RPC JSON。

`resolve_app` 仅查询应用信息；查询超时会交给 Pi 分析并提示检查手机连接，不会锁住执行通道或由底层自动重试。涉及 UI 的未确认调用暂缓后续动作；Pi 可用 `reconcile_action` 核实回执，用 `diagnose_phone` 读取设备状态与 Runner 日志，再制定下一步。诊断不会重放动作或自行解锁；本地调用进程尚未结束时连诊断请求也不发送。局域网 IP 变化或 Runner 退出后，先恢复 Runner、更新 `ICTRL_HOST` 并核查配对与实际读屏，再恢复之前已暂停的通道。

Runner 的 OCR 结果未携带应用标识时，Bridge 通过 `device_info.system` 核实当前前台应用和锁屏状态，不再补读可能已故障的控件树；只有确认未锁屏且仍在目标应用，OCR 坐标才能用于点击。`device_info` 仍共享 UI 队列，不能用作卡住时的存活探针；`operation_status` 和 `logs` 才绕过 UI 队列。无法核验或已切到其他应用时仍会拒绝派发。

执行预算仍为每轮 3000 次模型请求 / 6 小时，追问等待不计时，回答后重新计算。当前页面简单只读仍跳过额外规划；普通读屏通常两次模型调用，记忆保存/查询通常一次。Pi 不是推理加速器；不会承诺云端与 Runner 延迟消失。压缩只在接近上下文阈值时调用同一千问模型，没有每句话额外摘要和向量数据库。普通执行保留 384 token 短输出，SDK 上下文摘要独立使用 3276 token，避免长任务摘要被执行输出上限截断。仅模型请求可最多重试两次，不自动重试手机动作。

2026-10-17 本机加载 12 条测试任务后，空闲 Python Bridge RSS 约 37 MiB，新增 Node 约 83 MiB；固定版本依赖占磁盘约 111 MiB。这是单次空闲采样，不是长任务峰值或长期内存保证。

验证命令：`npm test`；在 `host/` 运行 `./.venv/bin/python -m unittest discover -s tests -v` 及 `./.venv/bin/python tests/test_tasks.py`。测试含真实管道、SQLite 重启、强杀 Node、去重、追问恢复、取消排空、证据和预算；本地测试不依赖云端。实机与云端报告保存在项目 `.runtime/`，迁移结果见根目录文档。

仍保留现有半双工语音行为：播报结束后收音；忙碌期间普通新话语不会变成并行任务，确认回答和取消走现有控制路径。3000 步压力测试、完整咖啡流程与长期 Runner 稳定性仍需独立验收。

语音指令在完整 ASR 结果持久化入队后立即播报“我已经收到了”，同一 request_id 只确认一次。短语在 Bridge 启动时预合成并缓存，确认播报与后台规划、执行并行；问题和最终结果仍通过原有播放回执控制收音。
