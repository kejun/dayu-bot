# 架构（2026-10-18）

## 组件职责

| 组件 | 当前职责 |
|---|---|
| ESP32-S3 / 固件 0.2.5 | PCM 采集、分档 VAD、句首预录、按键、播放、精灵状态、播放完成回执；不调用模型或直接控制手机 |
| `server.py` | WebSocket、认证、音频事务、后台 ASR、问题播报与听取、取消控制 |
| `tasks.py` / `pi_agent.py` | 串行队列、持久化后发布状态、恢复、管道工具调度及安全取消 |
| `host/pi/` | 常驻 Pi Durable 1.3.0、千问执行循环、SQLite 状态、上下文压缩和用户记忆 |
| `intent.py` / `direct.py` | 复用千问任务整理与校验；direct 的旧执行循环只用于显式回退 |
| `phone_tools.py` / `phone_worker.py` | 少量固定工具、受控参数、应用与只读限制、iCTRL 调用、快照和证据 |
| `speech.py` / `tts.py` | 千问云端 ASR / TTS，原生异步 I/O，可取消 |
| `agent.py` / `qwen.py` | 后端选择与可选 Hermes 适配；模型统一千问、关闭思考 |
| iCTRL Runner | iPhone 上的 XCUITest 服务，经加密 JSON-RPC `:8200` 提供界面、操作及持久动作回执 |

所有手机业务统一通过 iCTRL 操作真实 App；没有独立微信、邮箱或购物业务接口。默认后端是 `pi`，Hermes CLI 不在默认请求链路中。定时调度尚未接入。正式运行与恢复命令见 [Pi 运行时](../host/pi/README.md)。

## 连接与执行

```text
ESP32 ──Wi-Fi / WebSocket :8765── Bridge
                                 ├─ QwenAsr → 任务文本 → TaskManager
                                 ├─ 整理规范 → JSONL → Node / Pi → 千问
                                 │                       ↕
                                 │                 私有 SQLite
                                 │              ↓
                                 │          固定手机工具
                                 │              ↓
                                 │     worker → 官方加密客户端 / curl
                                 │              ↓
                                 │          iPhone iCTRL :8200
                                 └─ 问题或结果 → QwenTts → PCM → ESP32
```

USB 用于设备供电、固件烧录和串口调试；iPhone 的 Runner 测试会话目前仍依赖 Mac/Xcode。主机与设备、手机需要网络可达。项目 `.env` 中的千问服务地址按部署环境配置。

## 任务整理

复杂指令先调用同一千问模型的 `prepare_task`，输出 `goal`、`app`、`entry`、`steps`、`read_only` 等规范；辅助信息包括其他应用、限制、假设、待确认项和前置追问。当前界面只读请求可由本地规则直接生成规范。

- 保留用户原话与历次补充，规范不能丢掉预算、否定、数量或只读条件。
- “淘宝闪购”按既定约定走淘宝内闪购；用户明确指定独立 App 时遵循新指令。工具层校验根应用身份，避免同名服务误跳转。
- 配送位置、门店距离、营业状态、商品和价格来自实际页面；未决偏好交给用户回答，购物停在提交订单和付款前。
- 空辅助字段可省略或为 null；缺关键字段或规范无效时最多自动修正一次，两次共用 8 秒规划请求预算。校验通过前不派发新的手机动作。
- `intent.json` 保存原文、补充和规范；规划原始候选单独存档，事件日志区分 `phase=plan` 与 `phase=execute`。

## 模型与工具循环

主模型默认 `qwen-flash`，本机当前配置为 `qwen3.8-flash`。规划、执行及 Hermes 辅助模型统一千问，并固定 `enable_thinking=false`。无自动跨服务或跨后端重试。

模型固定关闭并行工具，提示每轮只调用一个；Pi 工具执行也设置为顺序。`open_app` 合并启动与首次读屏，`tap`、`type_text`、`scroll` 合并动作后的读屏；默认树读取，稀疏或确有需要时使用 OCR。精简快照保留文本、交互节点、省略和异常信息，完整原文可按快照编号补读。

快速启动由本机独立 iCTRL 仓库的 `launch_mode:"foreground"` 提供：确认切到前台和处理启动弹窗后返回，不等待首屏稳定；Bridge 随即读屏，空白或加载中最多有界重读。`ready` 保持 Runner 原有默认行为。

成功结果必须引用本任务工具证据，并且证据对应最近的修改状态；修改后的旧快照不能证明成功。RPC 异常、动作结果未知和成功核验分别处理，避免将不确定的点击或提交再次执行。

明确的 `find_element` / `-32602` / `No element matching label/id` 属于可恢复查找失败，Pi 将错误送回模型重新定位；严格匹配且已结束的 AX 无响应错误可改用 OCR。连续三次错误、连续四次界面无变化，或模型准备放弃时，Pi 根据原目标、限制、完成记录、错误和当前画面重新规划剩余步骤；最多三轮策略仍无进展才询问用户。新计划不能扩大应用、只读权限或丢弃限制。仅模型请求最多重试两次，未知的手机动作不按此规则重试。终态只播报可理解的中文错误，不把原始 RPC JSON 交给 TTS。

应用根身份将“股票 / 股市 / Stocks”归为同一个系统应用别名，仍通过真实应用解析结果获得 bundle ID。元素查找按当前树中唯一匹配的真实类型修正误猜类型；无标签输入框仅在当前视口内存在唯一对应类型节点时生成本地引用。点击只能使用同一快照及修改代次的引用，定位中心来自真实节点边界；任意模型坐标仍不开放。修改后旧引用失效，已完成点击不得反复重放。

## 动作超时与任务接续

旧实现把远端 UI 超时和本地主机进程无法清理都归为致命收尾异常，并将保护状态恢复到 Python FIFO。Runner 的 6 秒看门狗只结束 HTTP 回复，XCTest 动作可能仍在运行；主机收到超时后便暂停整个手机通道，后续任务也直接失败。缺少动作编号时，按方法名搜索日志又无法可靠区分相邻的同类动作。

现在把三件事分开处理：

1. 派发前将唯一 `operation_id`、参数和进度提交 Pi；Runner 按认证客户端保存回执后才排入 UI 队列。同编号、同参数返回已有记录，参数不一致拒绝，均不重复派发。
2. 超时只查询非 UI 通道 `operation_status`，默认核实 45 秒。`queued` / `running` 继续等待，`succeeded` 取回真实结果，再读取新画面接续原任务。日志仅辅助诊断，不能代替原编号的完成回执。
3. 暂未确认时保留任务进度为等待，允许 Pi 用 `reconcile_action` 核实、用 `diagnose_phone` 诊断，并在结束或询问前再核实一次。确认前不派发新的 UI 动作；普通远端超时不再冒充本地进程收尾失败。

Runner 重启时把在途回执改为 `unknown_after_restart`；旧结果载荷过期时保留编号，防止旧动作重放。这些状态不能当作成功证明。`resolve_app` 查询失败不锁 UI 通道；本地调用确实无法清理、旧版无编号动作或持久化故障仍保留人工核对保护。回执存储与客户端协议见 [iCTRL 文档](ictrl-setup.md)。

## 串行调度与执行预算

`DurableTaskManager` 复用 FIFO 队列，同一实例只运行一个手机任务；状态提交 Pi 后才向设备发布。等待用户回答时继续占住该位置，后续任务不抢占。相同 `request_id` 跨重启复用已有结果；显式提供 `dedup_key` 时可合并尚未结束的同类任务。

当前没有独立优先级调度，也没有接通定时任务。同一 Pi 数据目录的 Python flock 和 Node runtime.lock 防止 Bridge / CLI 并行占用。`bridge ask` 需先停 Bridge；禁止使用不同目录或回退后端并行操作同一手机。排队任务重启后按顺序继续，等待回答的任务恢复问题。带编号的在途动作在 Node/Bridge 中断后先查询原回执，再接续剩余目标；不重放动作。只有遗留或无法核实的保护需要停服核对后执行 `bridge pi-recover`，不能仅靠重启放行。

每个任务独立 Pi conversation；问题和回答对应关系与原始回答一并保留，避免“先问我”在回答后被重新当作未执行步骤。session 记忆按设备 owner 隔离，保存用户明确要求的偏好/笔记和当天临时偏好。复购只使用 `remember_order` 经当前真实完成订单详情核验的记录；缺失时查手机或追问，购物车不作为成交事实。记忆对话只提供记忆/追问工具，不增加手机规划调用。上下文接近阈值才触发同一千问模型压缩，摘要独立使用 3276 token，普通执行输出仍为 384 token；没有后台常驻推理、每轮摘要或向量服务。

| 预算 | 当前默认与作用域 |
|---|---|
| 执行步数 | `QWEN_MAX_STEPS=3000`，一次模型执行请求计一步；规划请求不计入此步数 |
| 每轮总时限 | `AGENT_TIMEOUT=21600` 秒，含本轮规划和执行，不含问题等待时间 |
| 单次模型请求 | 30 秒；规划两次请求合计最多 8 秒 |
| 单次手机请求 | 基础 8 秒；`page` / `page_source` / `screen_text` 至少 18 秒；合并工具可能调用多个 RPC |
| 原动作核实 | `PHONE_RECOVERY_TIMEOUT=45` 秒，只查询回执，不重发动作 |
| ASR / TTS | 各 15 秒 |

收到补充后，沿用原任务 ID 和对话历史，清理失效引用并重新规划；本轮执行步数与总时限重新计算。3000 步是配置上限，尚无完整 3000 步压力测试记录。

## 澄清与确认

语音采集分为空闲/取消监听（5 秒上限、500 毫秒静音）和完整指令/回答（30 秒、1200 毫秒）。固件 0.2.5 使用 34.5 dB 麦克风增益、500/250 RMS 起止门槛、连续两帧确认与 200 毫秒句首预录。设备在 20 秒唤醒窗口内开始采集即可，主机将 `command` 录音绑定该次唤醒会话，避免长句 ASR 返回时过期；完整指令提交后消费会话，不继续把背景话语当新任务。达到缓冲上限的任务或回答提示重说，不执行片段；无关的背景截断不触发提示。

Bridge 等待完整 ASR、持久化接收任务后，用启动时预合成的短语播报“我已经收到了”，同一 request_id 只确认一次；模型与手机任务并行继续。确认沿用 `speak` 音频事务，不代表任务完成，也不提前执行转写片段。

```text
processing → need_user：speaking → speak_done → listen → listening
                                                    ↓
                                             语音停顿后上传
                                                    ↓
                                               recognizing
                                             ↙             ↘
                                   识别为空/失败          有效回答
                                     listening          processing
```

TaskManager 在 `need_user` 等待回答事件，不调用下一轮 Agent。Bridge 向发起设备发送 `question` 并合成问题，设备显示说话动画且暂停收音。

设备写完问题 PCM，并通过静音尾部排空 I2S 最后语音后发送 `speak_done`；Bridge 校验设备归属、`request_id`、`question_seq` 和 `audio_id`，才发送 `listen`。收到匹配指令后设备显示“请说话”，VAD 收到的回答无需唤醒词，以 `answer_to` 和问题轮次绑定原任务。

识别失败或空结果重新开启同一问题的听取；语音回答始终先检查取消控制词。旧轮次、取消后的回答以及其他设备的回答不恢复当前任务。重连会重播未解决的问题；重复上传回执不会重启正在播放的问题。TTS 失败或静音时给出协议提示并转入听取，任务仍暂停。

设备在播放期间持续排空麦克风缓冲，避免恢复收音时带入旧回声。当前为播放结束后收音，语音不能打断正在播放的问题；物理键长按仍可取消。具体帧格式见[协议](protocol-v1.md)。

## 取消与结果真实性

物理键长按 2 秒与“小D 小D，取消任务”共用取消控制路径，控制帧不会被后台 ASR 阻塞。语音取消的目标在录音接收时绑定，迟到识别不能取消后来开始的任务。

1. 清除旧播报并阻止迟到转写、新模型动作和未派发的手机请求。
2. Pi abort 停止生成与后续工具，通过管道要求 Python 等待已派发的有界 iCTRL 调用返回；direct / Hermes 回退保持各自收尾逻辑。取消不会倒退已发生的手机操作。
3. 批量目标全部完成清理后再回报终态、播报“任务已经取消”。已经得到成功结果时保留成功，不伪称撤销。
4. 远端动作仍未确认时保留原编号，后续手机任务先核实其结束回执。不能确认本地调用已清理时返回 `unknown` 并持久化保护，核对并执行恢复命令后再启动 Bridge。

`launch_app` 的明确原生拒绝只有在方法、目标 bundle ID、错误码和固定消息全部匹配时才按普通启动失败处理，不暂停整个通道。通用 `-32000`、超时或未知错误不能据此放行。

## 日志与部署边界

Pi 数据默认在 `~/.dayu/pi/`：SQLite 保存状态和记忆，`plans/` 保存规范及规划候选，`traces/` 保存完整界面和手机事件。运行日志关联 request_id / conversation_id；不输出模型原始页面或凭据。最近 64 条证据摘要保存在任务状态，完整结果在 Pi transcript 和本地快照中，避免把页面反复复制进状态。回退 direct 使用 `.runtime/direct/`。这些记录包含用户输入和页面内容，保留在本地，不随 Git 分发。

固件问题轮次功能要求至少 `0.2.0`，完整长句与唤醒会话绑定要求至少 `0.2.2` 与 Bridge 配套，当前 `0.2.5` 包含拾音与句末响应优化。Runner 快速启动及持久动作回执改动在独立的 [iCTRL fork（50bcec4）](https://github.com/kejun/iCTRL/tree/50bcec4)。更新本仓库、更新手机 Runner 和烧录 ESP32 是三个部署步骤。配置优先级与命令见 [README](../README.md)，实测范围和待验收项见[开发计划](plan.md)。
